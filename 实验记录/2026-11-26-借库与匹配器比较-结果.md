# 借库与匹配器比较：结果

2026-11-26 · 方案见 [借库与匹配器比较-方案](2026-11-26-借库与匹配器比较-方案.md) · 原始数据 [借库与匹配器比较-数据.jsonl](2026-11-26-借库与匹配器比较-数据.jsonl) · 脚本 `tools/borrow_exp.py`

## 做法

- 试跑页：20 页，2,820 格。01 册：序 2、3，目錄 10、11，正文 50、51、86、104；02–05 册：20、40、60。
- 标签：先借全唐文跑一遍，20 页全部锚上，参校本对位给出 2,728 格的字（`align_ref.align_char`，不论 5a 认没认对，免得偏向全唐文）。参校本约 98%，所以首位对率上限也在 98% 左右。
- 每组：建一份**只含借来刻例**的 glyph.db（scope `human+auto`，本书库为空），复制工作区，`GUJI_GLYPH_DB` 指向它，从 `glyph_match` 跑到 `seed_admit`（`--force`）。
- 各库刻例数：全唐文 38,746，史記 5,896，殿本 8,780，全唐文加史記 44,642。

## 指标

- 覆盖：标签字在库里有刻例的格占比。
- 首位对、前五对：在有刻例的格里，候选首位（前五）是标签字的比例。己已巳、日曰折叠。
- 待审率：跑到 seed_admit 后没放行的格占全部 2,820 格的比例。这是冷启动首跑的数，本书还没有自己的字库。
- 借来的条目判 same 会被降成 unsure，所以生产 verdict 里 same 都是 0。这里另算「首位分 ≥ 0.996」的格及其中错字，只作参考。

耗时（云端 4 核 CPU，20 页 5a 到 seed_admit）：HOG 约 3–4 分钟；CNN 约 8–27 分钟，单页 5a 最慢 240 秒（含首次载模型、与其他组抢 CPU）。

## 结论

1. **借全唐文**。萬曆刻本和全唐文（清刻宋体）是同一族：覆盖 97%，首位对 85–90%。史記（寫本）一页都锚不上；殿本覆盖不到 80%，一半以上的页锚不上。
2. **CNN 比 HOG 好**。同一个全唐文库，通用 CNN 首位对 84.9%→90.2%，待审率 7.6%→5.9%。
3. **通用模型 base_v1 比专训模型好**。全唐文专训 89.4%，史記专训 89.1%，都不如通用的 90.2%。新书字体没进过训练时，合训的通用模型泛化更好。
4. **融合和单用差不多**。单用 CNN 待审略低（5.7% 对 5.9%），但首位分 ≥0.996 里出了 1 个错字；融合 0 错。先用融合（`fuse: mean`），更稳。
5. **加借史記收益很小**。覆盖 +0.9 点，待审 5.9%→5.7%，但 HOG 下多出 3 个高分错字。先不加。
6. 弱库对 CNN 的提升更大（殿本待审 66.6%→42.2%），说明 CNN 对字体差异更宽容，但还是救不回字体不同族的库。

## 建议配置

```yaml
# workspace.yaml
glyph_lib:
  borrow:
    - {from: 995ejelvk0, scope: human+auto}
# config/book_defaults.yaml 的 params
glyph_match:
  sim_model: {path: models/glyph_sim_base_v1/model.pt, fuse: mean}
```

## 局限

- 标签来自参校本（约 98%），绝对数有约 2% 噪声；各组面对的噪声相同，排序可信。下一步用首批约 200 格人审核对。
- 待审率是本书库为空时的冷启动数，不是目标 0.2% 的口径。
- 只有 20 页；01 册序、目錄各 2 页，样本小。
